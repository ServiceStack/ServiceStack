# ServiceStack.Blazor features

Reviewed 2026-11-11 against source HEAD `101038b4ba5a65650e02491e98c7c8a4e1d46f5f` and the local documentation checkout. This inventory describes source presence and the limited validation below, not confirmed published-package availability. Existing AGENTS.md supplies development rules; implementation determines the capability boundaries.

## Package and ownership

- [ServiceStack.Blazor.csproj](ServiceStack.Blazor.csproj) is a Razor class library targeting `net6.0;net8.0;net10.0`, with a ServiceStack.Client project reference and target-specific Microsoft HTTP, WebAssembly and authorization packages. Shared contracts and serialization arrive through that dependency graph.
- The richer CRUD/grid components are in `Components/Tailwind`; `Components/Bootstrap` supplies a smaller input/alert/loading set. These are not two equivalent component suites.
- The package contains UI components, a WASM auth provider, client registration and gateway-aware helpers. Server registration, server authentication/host-state transport, Identity integration, AutoQuery execution and file storage are owned elsewhere. Their availability is not an additional implementation inside this package.
- Server and WASM sample applications are present. Target-framework declarations and historical MAUI/Hybrid claims do not establish a tested MAUI, static SSR or every InteractiveAuto combination.

## Verification and observed gaps

On 2026-11-11 the net10.0 Razor library build passed with existing warnings; the optional token-gated Tailwind generation target was disabled. The four existing assertions in [BlazorSecurityTests](../../tests/ServiceStack.Blazor.Server.Tests/Tests/BlazorSecurityTests.cs) were invoked directly in a temporary net10.0 runner against the built library: local return URLs, required roles/permissions, HTML key/scalar encoding and dump-depth limits passed. This was not a run of the complete sample test project, browser tests or the other target runtimes. bUnit references and commented prerender tasks are present; they do not establish executable grid/form interaction coverage.

Two additional temporary probes reproduced source-level concerns without changing production code:

1. A label inserted into LookupValues was returned by GetOrFetchValueAsync for a different API client's base URL without fetching that API. The key has no client/user/tenant dimension. This establishes cross-client cache reuse; actual protected-data exposure in a deployed application was not tested. See [BLAZOR-001](plan/FEATURE-PROPOSALS.md#blazor-001-scope-and-bound-ui-lookup-state).
2. After SignInAsync, a simulated successful logout HTTP response left BlazorWasmAuthenticationStateProvider.IsAuthenticated and its returned ClaimsPrincipal authenticated. ApiResult.ClearErrors only clears Error. This establishes stale UI auth state, not bypass of server authorization. See [BLAZOR-002](plan/FEATURE-PROPOSALS.md#blazor-002-make-auth-state-transitions-explicit-and-testable).

Other source-backed investigation areas are cancellation/stale results, keyboard/focus lifetimes, upload buffering/status, virtualized data sources, render-mode initialization and generated-form dirty state. Missing APIs were searched in the owning implementation and adjacent owners; absence claims are bounded to this checkout. The shared Client metadata cache and global config need explicit ownership/lifetime review before introducing persistent component-state caching.

No production behavior was changed, no new feature was accepted, and no published release was confirmed by this documentation review. Do not infer accessibility compliance, performance, cloud-provider parity or complete Server/WASM/Hybrid parity from these checks.
